Guías Git y GitHub Versionar y compartir código
Todas las guías

Git y GitHub

Git guarda la historia de tu proyecto en tu PC; GitHub la publica en la nube para que otros la vean y colaboren. Primero lo que pasa en tu máquina, después lo que pasa en GitHub, y al final el flujo de trabajo de todos los días. Pensada para Windows, con la nota para Linux donde cambia algo.

Cómo leer esta guía. Cada bloque dice dónde ocurre lo que explica: LOCAL · tu PC es tu computadora, nadie más lo ve; REMOTO · GitHub es la copia en la nube, la que ven tus compañeros. Nada viaja de una a la otra hasta que vos lo pedís.

Sección 01

Instalar Git y elegir la terminal

Git es un programa que se instala en tu PC y se usa escribiendo comandos. No necesita internet ni cuenta en ningún lado: eso viene después, con GitHub.

Instalar local

Windows

Bajá Git for Windows de git-scm.com y hacé Siguiente a todo. Trae dos cosas: el comando git y una terminal llamada Git Bash.

Si en la instalación pregunta por "line endings", dejá la opción por defecto (Checkout Windows-style, commit Unix-style).

Linux

Casi siempre ya viene instalado. Si no:

# Ubuntu / Debian
sudo apt install git
# Fedora
sudo dnf install git

Qué terminal usar en Windows

TerminalComentario
Git BashLa recomendada. Usa los mismos comandos que Linux y Mac (ls, cd, pwd), así que todo tutorial de internet te sirve tal cual
Terminal de VS CodeLa misma Git Bash, pero adentro del editor. Abrila con Ctrl+ñ (o Ctrl+` en teclado inglés) y elegí "Git Bash" en el desplegable
PowerShell / CMDFuncionan, git es el mismo. Pero los comandos del sistema cambian (dir en vez de ls) y algunos ejemplos de internet no corren igual
Cómo se ven las rutas en Git Bash. Tu carpeta C:\Users\Ana\Documents aparece como /c/Users/Ana/Documents, con barras al derecho. Para ir a la carpeta del proyecto: cd /c/Users/Ana/Documents/proyecto. Un atajo: en el Explorador de Windows, click derecho sobre la carpeta → Open Git Bash here, y ya estás parado ahí.

Configurar tu nombre local

Git firma cada commit con un nombre y un mail. Se configura una sola vez por PC, en cualquier terminal, y corre igual en Windows y Linux:

git config --global user.name  "Ana Pérez"
git config --global user.email "ana@ejemplo.com"
git config --global init.defaultBranch main   # rama inicial: main

git config --list                             # ver qué quedó guardado
Usá el mismo mail que en GitHub. Todavía no la necesitás, pero cuando te crees la cuenta en GitHub, que sea con este mismo mail: así los commits que hagas en tu PC aparecen con tu nombre y tu foto cuando los subas.
Clave. Instalá Git for Windows, usá Git Bash (suelta o dentro de VS Code) y configurá nombre y mail una vez. Con eso ya tenés todo lo de la primera mitad de la guía: no hace falta cuenta, ni internet, ni GitHub.

Sección 02

Las tres zonas

Git no guarda "la última versión": guarda una foto cada vez que se lo pedís. Para entender cualquier comando alcanza con saber en cuál de tres lugares está tu archivo en cada momento. Los tres lugares están en tu PC.

Qué es cada una local

Los cuatro comandos del día a día local

Parado en la carpeta del proyecto, en Git Bash. Corren idéntico en Windows y Linux:

git init                     # crear el repositorio (una vez por proyecto)
git status                   # ¿en qué zona está cada archivo?
git add app.py               # mandar un archivo al staging
git add .                    # mandar todo lo modificado
git commit -m "Agrega el promedio"   # sacar la foto
¿Dónde quedó guardado? git init crea una carpeta oculta .git adentro de la del proyecto. Ahí está toda la historia. En Windows no se ve salvo que actives "Elementos ocultos" en el Explorador; no la toques ni la borres: sin ella, el proyecto deja de ser un repositorio.

Leer git status

Es el comando que más vas a tirar. Te dice, por zona, qué archivos tenés y qué comando corresponde:

git status
On branch main
Changes to be committed:            ← en staging, va en el próximo commit
        modified:   app.py

Changes not staged for commit:      ← modificado, todavía sin add
        modified:   README.md

Untracked files:                    ← archivo nuevo, Git ni lo mira aún
        datos.csv

Qué hace cada comando con las zonas

ComandoMueve
git add archivoTrabajo → Staging
git restore --staged archivoStaging → Trabajo (deshace el add, no toca el archivo)
git commit -m "…"Staging → Repositorio
git restore archivoDescarta los cambios del trabajo y vuelve al último commit
git diffMuestra la diferencia entre Trabajo y Staging
git diff --stagedMuestra la diferencia entre Staging y el último commit
git log --onelineLista los commits del repositorio, uno por línea
git restore archivo no tiene deshacer. Tira los cambios que no commiteaste y no hay forma de recuperarlos. Antes de usarlo, git diff para ver qué estás por perder.
Si en Windows ves "LF will be replaced by CRLF". Es un aviso, no un error. Windows y Linux terminan las líneas de texto con caracteres distintos y Git los está convirtiendo para que a nadie le aparezca todo el archivo como "modificado". Se puede seguir tranquilo. Si te molesta el mensaje: git config --global core.autocrlf true (en Linux sería input).
Qué es un commit. Una foto completa del proyecto, con autor, fecha, mensaje y un identificador de 40 caracteres (el hash, tipo a3f9c1e en corto). Nunca se modifica: si te equivocaste, hacés otro commit que corrige. Por eso Git es tan seguro: lo commiteado no se pierde.
Clave. Commiteá chico y seguido. Un commit por cada cambio con sentido propio ("agrega la carga del CSV", "corrige el promedio") y no uno gigante al final del día. Es gratis, queda en tu PC, y cuando algo se rompa vas a poder ver exactamente en qué paso pasó.

Sección 03

Leer la historia

Después de unos commits, el valor de Git está en poder mirar hacia atrás: qué cambió, cuándo y quién. Y en decirle qué archivos no tiene que mirar nunca.

git log local

git log                      # todo: hash largo, autor, fecha, mensaje
git log --oneline            # una línea por commit, lo que más se usa
git log --oneline -5         # los últimos cinco
git log --oneline --graph    # con el dibujo de las ramas
git log -- app.py            # solo los commits que tocaron ese archivo
a3f9c1e (HEAD -> main) Agrega el promedio
7b21d04 Carga el CSV con pandas
c0ffee1 Primer commit

Se lee de arriba hacia abajo: el más nuevo primero. HEAD es "donde estás parado", casi siempre el último commit de la rama actual. Si el listado es largo, se sale con q.

git diff: qué cambió exactamente

ComandoCompara
git diffLo que editaste y todavía no hiciste add
git diff --stagedLo que ya está en staging contra el último commit: lo que va a entrar
git diff a3f9c1e 7b21d04Dos commits entre sí
git show a3f9c1eUn commit: su mensaje y todo lo que cambió
git show HEAD~1El commit anterior al actual (~2, dos atrás, etc.)
 
git diff
--- a/app.py
+++ b/app.py
@@ -3,4 +3,4 @@
 datos = pd.read_csv("ventas.csv")
-promedio = datos.sum() / len(datos)
+promedio = datos["monto"].mean()
 print(promedio)

Las líneas con - son lo que había, las con + lo que hay ahora. Las que no tienen signo son contexto, para ubicarse.

.gitignore: lo que Git no tiene que ver

Un archivo de texto llamado .gitignore, en la carpeta raíz del proyecto, con un patrón por línea. Lo que matchea no aparece en git status ni entra con git add .

# .gitignore típico de un proyecto de datos en Python
__pycache__/
.ipynb_checkpoints/
venv/
.env                 # contraseñas y claves: NUNCA suben
*.csv                # datos pesados, se comparten por otro lado
*.xlsx
Thumbs.db            # basura de Windows
desktop.ini
.vscode/
PatrónIgnora
archivo.txtEse archivo, en cualquier carpeta
carpeta/Esa carpeta con todo lo que tenga
*.csvTodo lo que termine en .csv
!datos/ejemplo.csvExcepción: este sí, aunque sea .csv
# textoComentario
Crear un archivo sin nombre en Windows. El Explorador no deja guardar un archivo llamado solo .gitignore desde algunos programas. Lo más fácil: en VS Code, botón derecho en la carpeta → New File → escribir .gitignore. O desde Git Bash: touch .gitignore.
Si ya lo commiteaste, ignorarlo no alcanza. .gitignore solo frena archivos que Git todavía no sigue. Para sacar uno que ya entró (sin borrarlo de tu disco): git rm --cached archivo, y commit. Si era una contraseña, además cambiala: quedó en la historia.
Clave. Creá el .gitignore antes del primer git add ., no después. Y git log --oneline antes de cada push: si un mensaje no se entiende, es el momento de arreglarlo, no cuando ya lo vieron todos.

Sección 04

Deshacer

La pregunta que más se hace en Git es "¿cómo vuelvo atrás?". La respuesta depende de en qué zona está el error. Todo esto es local: mientras no hayas hecho push, deshacer no afecta a nadie.

Según dónde está el error local

Quiero…ComandoRiesgo
Tirar lo que edité en un archivo, volver al último commitgit restore app.pySe pierde
Sacar un archivo del staging (deshacer el add)git restore --staged app.pyNinguno
Cambiar el mensaje del último commitgit commit --amend -m "…"Solo si ya lo pusheaste
Me olvidé un archivo en el último commitgit add x · git commit --amend --no-editSolo si ya lo pusheaste
Deshacer el último commit pero conservar los cambiosgit reset --soft HEAD~1Ninguno
Borrar el último commit y sus cambios, como si no hubiera existidogit reset --hard HEAD~1Se pierde
Anular un commit viejo, que ya vieron otrosgit revert a3f9c1eNinguno
Guardar lo que estoy haciendo para después, sin commiteargit stashNinguno

reset o revert: la diferencia que importa

Los tres reset

ComandoMueve HEAD atrás y…
git reset --soft HEAD~1deja los cambios en staging, listos para recommitear
git reset HEAD~1deja los cambios en el directorio de trabajo, sin add (el por defecto, --mixed)
git reset --hard HEAD~1tira todo: el commit y los cambios

stash: guardar a medias

Estás en la mitad de algo, no está para commit, y tenés que cambiar de rama o probar otra cosa con el proyecto limpio.

git stash                    # guarda los cambios y deja todo como el último commit
git stash list               # ver qué hay guardado
git stash pop                # traer de vuelta lo último guardado
"Borré un commit con reset --hard y lo necesito". Git no lo borró de verdad, todavía. git reflog lista todo lo que fue HEAD en las últimas semanas, incluido el commit que "desapareció". Copiás su hash y git reset --hard ese-hash. Lo único que no se recupera es lo que nunca se commiteó.
Nunca reset ni --amend sobre commits que ya pusheaste. Tu historia y la de GitHub dejan de coincidir, el próximo push falla y arreglarlo involucra a todo el equipo. Para eso existe revert.
Clave. Regla simple: antes del push, reset y --amend son libres; después del push, solo revert. Y ante la duda, primero git status y git log --oneline: la mitad de las veces el problema no es el que parecía.

Sección 05

Ramas

Una rama es una línea de trabajo separada. Probás algo sin tocar lo que funciona, y cuando está listo lo unís. Es lo que hace posible que varias personas trabajen en lo mismo sin pisarse, y también lo que te permite experimentar solo.

Cómo se ve local

Recetario

git branch                   # listar las ramas; la actual con *
git switch -c grafico        # crear una rama y pasarse a ella
git switch main              # volver a main
git switch grafico           # ir a una rama que ya existe

# … trabajar y commitear en grafico …

git switch main              # pararse en la rama que va a RECIBIR
git merge grafico            # traer los commits de grafico a main
git branch -d grafico        # borrar la rama, ya está integrada
switch o checkout. En tutoriales viejos vas a ver git checkout -b grafico y git checkout main. Hacen lo mismo. switch es más nuevo (2019) y solo cambia de rama, que es más difícil de usar mal. Usá switch; entendé checkout cuando lo veas.

Qué pasa con los archivos al cambiar de rama

Git reemplaza el contenido de la carpeta por el de la rama a la que vas. Si abriste el archivo en VS Code, lo vas a ver cambiar solo. Es normal: es la misma carpeta mostrando otra versión.

SituaciónQué hace Git
Todo commiteadoCambia sin problemas
Hay cambios sin commitear que no chocan con la otra ramaCambia y se lleva los cambios con vos
Hay cambios sin commitear que sí chocanSe niega: "Please commit your changes or stash them". Commiteás o git stash

Los dos tipos de merge

TipoCuándo pasaResultado
Fast-forwardmain no se movió desde que creaste la ramaGit solo adelanta la etiqueta main; no hay commit de merge
Merge de tres víasLas dos ramas tienen commits nuevos (el dibujo de arriba)Git crea un commit de merge con dos padres. Si tocaron las mismas líneas, hay conflicto
El error clásico: commitear en la rama equivocada. Hiciste tres commits creyendo que estabas en grafico y estabas en main. git status siempre dice arriba On branch …: leelo antes de commitear. Si ya pasó y no pusheaste: git branch grafico (crea la rama apuntando acá), git reset --hard origin/main (devuelve main a como está en GitHub), y listo.
Clave. main siempre funciona; lo que estás haciendo va en una rama. Es la única regla de ramas que necesitás para trabajar en equipo, y también sola: si el experimento sale mal, git switch main y git branch -D experimento, sin arrepentimientos.

Sección 06

Conflictos

Un conflicto es cuando dos ramas cambiaron las mismas líneas del mismo archivo y Git no puede decidir cuál vale. No es un error ni algo que rompiste: es Git pidiéndote que elijas. Se resuelve siempre en tu PC.

Cómo aparece local

git merge grafico
Auto-merging app.py
CONFLICT (content): Merge conflict in app.py
Automatic merge failed; fix conflicts and then commit the result.

Git deja el archivo con las dos versiones marcadas. Al abrirlo ves esto:

datos = pd.read_csv("ventas.csv")
<<<<<<< HEAD
promedio = datos["monto"].mean()          # ← lo de main (donde estás)
=======
promedio = round(datos["monto"].mean(), 2) # ← lo que trae grafico
>>>>>>> grafico
print(promedio)

Los cuatro pasos

01git status para ver qué archivos están en conflicto (both modified)
02Abrir cada uno, decidir qué queda (una versión, la otra, o una mezcla) y borrar las marcas <<<<<<<, ======= y >>>>>>>
03Probar que el archivo anda: correr el script, abrir el notebook
04git add app.py y git commit (sin -m: Git ya propone el mensaje "Merge branch…")

En VS Code es más fácil

Al abrir un archivo en conflicto, VS Code pinta las dos versiones y pone botones arriba de cada bloque: Accept Current Change (la de tu rama), Accept Incoming Change (la que viene), Accept Both. Después del click, quedan los pasos 3 y 4 igual.

Si te arrepentís

git merge --abort            # cancelar el merge y volver a como estaba
Cuándo aparece un conflictoQué lo dispara
Al unir ramas en tu PCgit merge
Al traer cambios de GitHub que chocan con los tuyosgit pull (que por dentro es un merge)
En un pull requestGitHub avisa que no puede mergear; se resuelve en tu PC con git merge main y push
Al aplicar un stashgit stash pop sobre archivos que cambiaron
Los notebooks son un caso aparte. Un .ipynb es JSON con las salidas de las celdas adentro, así que dos personas ejecutándolo generan conflicto aunque no hayan tocado el código. Antes de commitear un notebook: Clear All Outputs. Y, si se puede, la lógica en un .py.
Clave. Los conflictos se achican con dos hábitos: git pull seguido, para que las diferencias con los demás sean chicas, y ramas cortas, que se integran en días y no en semanas. Un conflicto de tres líneas se resuelve en un minuto; uno de tres semanas, no.

Sección 07

Qué es GitHub

Todo lo anterior pasó en tu PC. GitHub es un sitio web que guarda una copia de tu repositorio en la nube: para tener respaldo, para trabajar desde otra máquina y, sobre todo, para que otros puedan ver el código y colaborar.

Git y GitHub no son lo mismo

GitGitHub
Qué esUn programaUn sitio web (de Microsoft desde 2018)
Dónde viveEn tu PC En la nube
NecesitaNada: ni internet ni cuentaCuenta gratuita e internet
Sirve paraGuardar la historia, ramas, deshacerCompartir, revisar, discutir, publicar
AlternativasMercurial, SVN (casi no se usan)GitLab, Bitbucket (mismo Git, otro sitio)

Crear la cuenta remoto

En github.com/signup, gratis. Dos decisiones que después cuestan cambiar:

01El nombre de usuario va a estar en la URL de todos tus proyectos (github.com/tu-usuario/proyecto) y es lo que vas a poner en un CV. Corto, sin números raros.
02El mail: el mismo que pusiste en git config user.email. Si no coinciden, tus commits aparecen sin tu foto, como de un desconocido.

Crear un repositorio remoto

Botón + arriba a la derecha → New repository.

CampoQué poner
Repository nameEl mismo nombre que la carpeta en tu PC, en minúsculas y con guiones: analisis-ventas
Public / PrivatePúblico lo ve cualquiera (bien para portfolio). Privado solo vos y a quien invites (bien para un trabajo de la cursada con datos que no son tuyos)
Add a READMENo si ya tenés el proyecto en tu PC: querés el repo vacío para subir el tuyo. Sí si arrancás de cero y vas a clonar
.gitignorePlantilla Python, si arrancás de cero
LicenseMIT si querés que cualquiera lo use. Se puede agregar después

Demostrarle a GitHub que sos vos

Leer un repo público no pide nada. Escribir (push) sí: GitHub tiene que saber que sos quien dice tu cuenta. La contraseña de la web no sirve desde la terminal desde 2021.

Windows: no hay que hacer nada

Git for Windows trae el Git Credential Manager. La primera vez que hagas push se abre el navegador, iniciás sesión en GitHub, autorizás, y queda guardado en el Administrador de credenciales de Windows. No lo vuelve a pedir.

Linux: token o SSH

Token: en GitHub, Settings → Developer settings → Personal access tokens, generás uno con permiso repo y lo pegás cuando la terminal pide contraseña. Para que lo recuerde: git config --global credential.helper store.

SSH: ssh-keygen -t ed25519, copiar el contenido de ~/.ssh/id_ed25519.pub en Settings → SSH keys, y usar las URL que empiezan con git@github.com:.

Qué se ve en la página de un repo. Arriba, las pestañas: Code (los archivos y el README), Issues (tareas y problemas), Pull requests (cambios propuestos), Actions (automatizaciones), Settings. El botón verde Code da la URL para clonar. El desplegable de la izquierda cambia de rama.
Clave. GitHub es la copia pública de lo que Git ya guarda en tu PC. Sin GitHub, Git sigue funcionando entero; sin Git, GitHub es solo una carpeta en internet. Aprendé a manejar el de tu máquina y el otro es apretar botones.

Sección 08

Conectar local y remoto

Tu repositorio y el de GitHub son dos copias independientes. Nada pasa de una a la otra solo: vos subís con push y bajás con pull. Cuatro comandos cubren todo el tráfico.

El tráfico entre las dos copias

Caso A: el proyecto ya está en tu PC local

Creaste el repo en GitHub vacío (sin README). GitHub muestra estos mismos comandos en la página del repo recién creado:

# conectar con el repo de GitHub
git remote add origin https://github.com/ana/proyecto.git
# subir main; -u solo la primera vez
git push -u origin main

git remote -v                # ver a dónde está conectado

Caso B: el proyecto está en GitHub y lo querés en tu PC

De un compañero, de un profesor, o tuyo desde otra máquina. Botón verde Code → copiar la URL:

cd /c/Users/Ana/Documents    # pararse DONDE querés la carpeta
git clone https://github.com/ana/proyecto.git
cd proyecto                  # clone creó la carpeta, con origin ya configurado

Todos los días: push y pull

git pull                     # ANTES de empezar: traer lo de los demás
# … trabajar, add, commit …
git push                     # al terminar: subir tus commits
ComandoDirecciónQué hace
git clone URLnube → PCUna sola vez: crea la carpeta con el repo completo
git pushPC → nubeSube los commits de la rama actual
git pullnube → PCBaja los commits nuevos y los mergea en tu rama
git fetchnube → PCBaja pero no mergea: solo actualiza origin/main para que puedas mirar
git remote -v—Muestra a qué URL apunta origin

Los tres mensajes que vas a ver

MensajeQué pasó y qué hacer
! [rejected] … (fetch first)Alguien subió commits que no tenés. git pull, resolver conflictos si hay, y de nuevo git push
Your branch is behind 'origin/main'Te falta bajar. git pull
Your branch is ahead of 'origin/main' by 2 commitsTenés dos commits sin subir. git push cuando quieras
"Please tell me who you are" o pide usuario y contraseña. Lo primero es que falta el git config de la sección 01. Lo segundo, en Windows, es la ventana del Credential Manager: iniciás sesión en el navegador una vez. En Linux, la "contraseña" es el token, no la de la web.
Nunca git push --force sobre main. Reemplaza la historia de GitHub por la tuya y borra los commits de los demás. Si un push es rechazado, la respuesta es pull, no fuerza. Lo vas a ver sugerido en internet: es para ramas propias, y con cuidado.
Clave. pull al empezar, push al terminar, y git status en el medio cuando dudes: la línea ahead / behind te dice exactamente si te falta subir o bajar. Con eso, la copia de tu PC y la de GitHub nunca se alejan demasiado.

Sección 09

Pull requests

Un pull request (PR) es la forma de decir "hice esto en una rama, ¿lo sumamos a main?". Es donde se revisa el código antes de que entre, y es la dinámica central de trabajar en equipo en GitHub. Mitad pasa en tu PC (la rama, los commits, el push) y mitad en la web de GitHub (abrir el PR, revisar, mergear).

El ciclo completo

La rama y el push local

git switch -c grafico          # crear la rama y pararse en ella
# … editar, git add, git commit, las veces que haga falta …
git push -u origin grafico     # subirla a GitHub (-u solo la primera vez)
remote: Create a pull request for 'grafico' on GitHub by visiting:
remote:   https://github.com/ana/proyecto/pull/new/grafico

Git mismo te da el enlace. Abrilo, o entrá al repo en GitHub: aparece un botón amarillo Compare & pull request.

La primera vez que hacés push en Windows se abre una ventana de GitHub pidiendo que inicies sesión en el navegador. Es el Git Credential Manager, que viene con Git for Windows: aceptás una vez y no te lo vuelve a pedir. En Linux no hay ventana: se usa un token o una clave SSH, que se ve en la sección 07.

Abrir el PR remoto

Esto es en el navegador, en la página del repo en GitHub:

CampoQué poner
base ← comparemain ← tu rama. Es decir: "quiero llevar mi rama a main". Verificalo, es el error más común
TítuloQué hace el cambio, en una línea: "Agrega gráfico de ventas por mes"
DescripciónPor qué se hizo, cómo probarlo, qué queda pendiente. Si resuelve un issue: Closes #12 lo cierra solo al hacer merge
ReviewersA quién le pedís que lo mire. Si es un trabajo de la cursada, a tus compañeros

La revisión remoto

En la pestaña Files changed se ve el diff completo y cualquiera puede comentar línea por línea.

EstadoSignifica
CommentUna opinión, no bloquea nada
ApproveEstá bien, se puede mergear
Request changesHay algo que corregir antes de que entre
DraftTodavía no está para revisar; lo abrís así para mostrar el avance

Si te piden cambios local

No hay que abrir otro PR. Volvés a tu PC, seguís commiteando en la misma rama y hacés push: el PR en GitHub se actualiza solo con los commits nuevos.

# te pidieron cambiar el color del gráfico
# … editás …
git add grafico.py
git commit -m "Usa la paleta del proyecto en el gráfico"
git push                       # sin -u: la rama ya sabe adónde ir

El merge remoto

Con el PR aprobado, el botón Merge pull request integra la rama en el main de GitHub. Ahí mismo ofrece borrar la rama: aceptá. Hay tres variantes del botón:

OpciónQué hace con la historiaCuándo
Merge commitSuma todos los commits de la rama más uno de mergeLa opción por defecto; sirve siempre
Squash and mergeAplasta todos los commits de la rama en uno soloCuando la rama tiene muchos commits chicos tipo "fix", "otra vez"
Rebase and mergeCopia los commits uno a uno sobre main, sin commit de mergeHistoria lineal; en equipos que lo acordaron

La vuelta a casa local

El merge pasó en GitHub: el main de tu PC todavía no sabe nada. Hay que traerlo:

git switch main
git pull                       # tu main local recibe el cambio mergeado
git branch -d grafico          # borrar la rama local, ya cumplió
"This branch has conflicts that must be resolved". Alguien cambió en main las mismas líneas que vos. GitHub no deja mergear hasta que lo resuelvas, y eso se hace en tu PC: git switch grafico, git merge main, arreglar los archivos marcados, commit y push. El PR se actualiza y el botón vuelve a verde.
¿Y si el repo no es mío? Mismo flujo, con un paso más: primero hacés un fork (una copia del repo en tu cuenta de GitHub), la clonás a tu PC, trabajás ahí y el PR va de tu fork al repo original. Así se contribuye a cualquier proyecto abierto sin pedir permiso de escritura.
Clave. Un PR chico se revisa en cinco minutos y se aprueba; uno de cuarenta archivos se posterga para siempre. Una rama, un cambio, un PR. Si te das cuenta de que estás tocando dos cosas distintas, son dos ramas.

Sección 10

Colaborar y publicar

Lo que GitHub agrega por encima de Git: un lugar para organizar el trabajo, presentar el proyecto y dejar que otros participen. Todo esto pasa en el navegador.

Sumar compañeros a un repo remoto

Para un trabajo en grupo, una persona crea el repo y suma al resto: Settings → Collaborators → Add people, por nombre de usuario. Cada uno recibe una invitación por mail, acepta, y ya puede hacer push. Después, cada uno clona a su PC y trabaja con ramas y pull requests.

Issues: la lista de tareas

Cada issue es un ticket: un bug, una tarea, una idea. Tiene número, título, descripción, responsable y etiquetas. Es donde se discute antes de escribir código, y sirve como lista de pendientes del grupo.

En el textoHace
#12Enlaza al issue 12 (en commits, PRs, otros issues)
@usuarioLe avisa a esa persona
Closes #12En la descripción de un PR: al mergearlo, cierra el issue solo
- [ ] tareaCasilla para marcar; GitHub muestra el progreso

Fork: colaborar en un repo ajeno

Si no sos colaborador, no podés hacer push. El camino es copiar el repo a tu cuenta (botón Fork), trabajar en la copia, y proponer el cambio con un PR desde tu fork hacia el original. Así funciona todo el código abierto.

# 1. En GitHub: botón Fork → aparece github.com/ana/proyecto-ajeno
# 2. clonar TU copia
git clone https://github.com/ana/proyecto-ajeno.git
cd proyecto-ajeno
git switch -c corrige-typo         # 3. rama, cambios, commit
git push -u origin corrige-typo    # 4. subir a tu fork
# 5. En GitHub: Compare & pull request → el PR va al repo original

README: la portada del proyecto

Un archivo README.md en la raíz se muestra solo en la página del repo. Está escrito en Markdown. Lo mínimo que tiene que responder: qué es, cómo se corre, con qué datos.

## Autores

GitHub Pages: publicar como sitio web

Si el repo tiene un index.html, GitHub lo sirve gratis como página. Settings → Pages → Source: Deploy from a branch → main. En un minuto queda en tu-usuario.github.io/proyecto. Esta guía que estás leyendo está publicada así.

La licencia. Sin un archivo LICENSE, legalmente nadie puede usar tu código aunque sea público. MIT es la más simple: "usalo como quieras, no me hago responsable". GitHub la agrega con un click en Add file → Create new file → LICENSE.
Clave. Un repo con README claro, issues abiertos y PRs revisados dice más de cómo trabajás que cualquier renglón del CV. Tratá tus trabajos de la cursada como si alguien los fuera a leer, porque alguien los va a leer.

Sección 11

El flujo de un equipo

Todo lo anterior, encadenado como pasa de verdad en un grupo. Se llama feature branch workflow y es lo que vas a encontrar en casi cualquier equipo: una rama por tarea, un PR por rama, main siempre sano.

Un día de trabajo

El mismo día, en comandos local

# 1. arrancar al día con lo último
git switch main
git pull

# 2. una rama para la tarea (issue #7: agregar gráfico de barras)
git switch -c grafico-barras

# 3. trabajar; commitear cada paso con sentido
git add grafico.py
git commit -m "Agrega gráfico de barras por categoría"
git add grafico.py
git commit -m "Ordena las barras de mayor a menor"

# 4. subir la rama
git push -u origin grafico-barras

# 5-7. en GitHub: abrir PR "Closes #7", esperar revisión, merge

# 8. volver a main con el cambio ya integrado
git switch main
git pull
git branch -d grafico-barras

Si la tarea dura varios días

main avanza mientras trabajás. Cada tanto, traé esos cambios a tu rama así el PR final no choca:

git switch main
git pull                     # actualizar main
git switch grafico-barras
git merge main               # traer lo nuevo de main; conflictos ahora, chicos

Nombres de rama

BienPor qué
grafico-barrasDice qué hace, minúsculas, guiones
fix-promedio-nulosUn prefijo por tipo ayuda: fix-, docs-, exp- para experimentos
ana/limpieza-csvCon el nombre adelante, en equipos donde cada uno tiene varias
prueba, nueva, rama2, finalNo dicen nada; en una semana nadie sabe qué tienen
Trabajando solo también sirve. Sin revisores el PR parece burocracia, pero deja un registro legible de qué hiciste y cuándo, y te obliga a mirar tu propio diff antes de mergear. Muchos errores se ven ahí. Como mínimo: ramas para lo que no sabés si va a funcionar.
Clave. Memorizá el ciclo, no los comandos: actualizar → rama → commits → push → PR → merge → actualizar. Los comandos salen solos después de la tercera vez. Lo que no se olvida es el orden.

Sección 12

Buenos commits

La historia la van a leer otros (y vos en tres meses, que es lo mismo). Un commit bien hecho se entiende sin abrir el diff. Cuesta diez segundos más y se paga solo la primera vez que buscás dónde se rompió algo.

Qué va en un commit

BienMal
TamañoUn cambio con sentido propio"Todo lo de hoy" (12 archivos, 3 temas)
EstadoEl proyecto funciona después del commitCódigo a medias que rompe el script
ContenidoSolo lo que dice el mensajeEl cambio, más un reformateo, más un archivo de prueba
FrecuenciaVarios por díaUno por semana

Cómo escribir el mensaje

Un título de hasta 50 caracteres, en presente, que complete la frase "este commit…". Si hace falta explicar el porqué, una línea en blanco y un párrafo:

git commit -m "Corrige el promedio cuando hay montos nulos"

# con cuerpo: git commit sin -m abre el editor
Corrige el promedio cuando hay montos nulos

mean() ya ignora los NaN, pero el conteo manual con len() los
incluía y bajaba el resultado. Cierra #14.
Mensaje
BienAgrega la carga del CSV de ventas
BienElimina columnas duplicadas del dataset
BienDocumenta cómo correr el análisis
Malcambios
Malarreglado
Malasdfgh
MalAgregué el gráfico y también arreglé el csv y saqué prints
Si te quedó abierto un editor raro. git commit sin -m abre el editor configurado, que en Windows suele ser Vim: escribís, Esc, :wq, Enter. Para que use VS Code: git config --global core.editor "code --wait". Se agradece.

Commits parciales: elegir qué entra

Tocaste dos cosas en el mismo archivo y querés dos commits. Se puede:

git add -p app.py            # bloque por bloque: y (sí), n (no), s (partir)
git commit -m "Corrige el promedio"
git add app.py               # lo que quedó
git commit -m "Renombra las columnas a minúsculas"

Lo que nunca se commitea

01Contraseñas, tokens, claves de API. Ni en un repo privado: van en .env, que está en el .gitignore
02Datos pesados o con información personal. Un CSV de 300 MB hace lento cada clone para siempre
03Cosas generadas: __pycache__, venv/, salidas de notebooks, gráficos que se regeneran
04Configuración personal del editor (.vscode/) y basura del sistema (Thumbs.db, desktop.ini)
Clave. Antes de escribir el mensaje, git diff --staged. Si no podés resumir lo que ves en una línea, son dos commits. Si podés, esa línea es el mensaje.

Sección 13

Git desde VS Code

Todo lo de esta guía se puede hacer con botones en VS Code, que ya trae Git integrado. Conviene saber a qué comando equivale cada botón: cuando algo sale raro, la terminal explica y el botón no.

La pestaña Source Control local

Ícono de las tres bolitas en la barra de la izquierda, o Ctrl+Shift+G. Muestra las mismas zonas que git status:

En VS CodeEquivale a
ChangesDirectorio de trabajo: archivos modificados sin add
Staged ChangesStaging
Botón + junto al archivogit add archivo
Botón − en Stagedgit restore --staged archivo
Flecha ↶ (Discard)git restore archivo — con la misma advertencia: no vuelve
Cuadro de texto + Commitgit commit -m "…"
Botón Sync Changesgit pull seguido de git push
Menú ··· → Branch → Create Branchgit switch -c nombre

Lo que se ve en el editor

SeñalSignifica
Barra de estado, abajo a la izquierdaLa rama actual. Click para cambiar de rama (git switch)
Número junto a la rama, ↓2 ↑1Commits para bajar y para subir (behind / ahead)
Barritas de color en el margenVerde: líneas nuevas; azul: modificadas; triángulo rojo: borradas. Click para ver el diff
Letra junto al archivo en el exploradorM modificado · U nuevo (untracked) · D borrado
Botones Accept Current / IncomingUn archivo en conflicto: elegir versión y borrar las marcas

Extensiones que ayudan

ExtensiónPara
Git GraphVer las ramas dibujadas, como git log --graph pero lindo
GitLensVer junto a cada línea quién la escribió y en qué commit (git blame)
GitHub Pull RequestsAbrir y revisar PRs sin salir del editor
GitHub Desktop. Programa aparte, gratuito, de GitHub. Más simple que VS Code para clone, commit, push y pull, y muy claro para ver diffs. Buena opción si la terminal te asusta al principio; los conceptos son los mismos.
Clave. Usá los botones para lo repetitivo (add, commit, sync) y la terminal para lo que necesite pensar (deshacer, ramas, conflictos). Y la terminal de VS Code ya es Git Bash: están a un Ctrl+ñ de distancia.

Recetario y errores frecuentes

Todo lo que se repite, en una página para tener a mano.

Los comandos, por zona

ComandoHaceDónde

git statusQué hay en cada zona, en qué rama estás

Situaciones que siempre vuelven

# Empezar un proyecto nuevo y subirlo
git init
git add .
git commit -m "Primer commit"
git remote add origin https://github.com/ana/proyecto.git
git push -u origin main

# Bajar un proyecto de un compañero
git clone https://github.com/juan/proyecto.git

# Una tarea, de punta a punta
git switch main && git pull
git switch -c mi-tarea
# … add, commit …
git push -u origin mi-tarea
# PR en GitHub → merge
git switch main && git pull

# Me olvidé de crear la rama y commiteé en main (sin push todavía)
git branch mi-tarea
git reset --hard origin/main
git switch mi-tarea

# Commiteé un archivo que debía estar ignorado
echo "datos.csv" >> .gitignore
git rm --cached datos.csv
git commit -m "Deja de seguir datos.csv"

Los errores que más se repiten

01Hacer add y creer que ya está guardado: sin commit no hay foto
02Hacer commit y creer que ya está en GitHub: sin push sigue solo en tu PC
03Commitear en main en vez de en una rama
04Empezar a trabajar sin pull y chocar con lo que subieron otros
05git add . sin .gitignore: suben el venv, los datos y las claves
06Resolver un conflicto sin borrar las marcas <<<<<<< y commitearlas
07reset --hard o push --force sobre algo que ya vieron otros
08Mensajes de commit tipo "cambios", "final", "final2"
09Correr git init adentro de una carpeta que ya es repo (o en C:\Users\Ana entera)
10Subir un notebook con las salidas y generar conflictos cada vez que alguien lo ejecuta

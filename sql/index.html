Guías SQL Consultas sobre bases relacionales
Todas las guías

SQL

Consultar bases relacionales, en PostgreSQL y SQL Server a la vez. El código va en un solo bloque cuando corre igual en los dos motores, y en dos columnas cuando cambia.

Sección 01

Los dos motores

SQL es un estándar, pero ningún motor lo implementa igual. Estas dos son las bases relacionales más usadas fuera del mundo web chico, y lo que aprendas en una te sirve casi entero en la otra.

Qué es cada una

PostgreSQL

Motor libre y gratuito, mantenido por una comunidad desde 1996. Corre en Linux, Windows y Mac. Es el más apegado al estándar SQL y el más extensible: se le agregan capacidades con extensiones, como PostGIS para datos geográficos.

Consola: psql · Interfaz: pgAdmin, DBeaver · Puerto 5432

SQL Server

Motor de Microsoft, comercial, con una edición Express gratuita y limitada. Su dialecto se llama T-SQL. Muy presente en empresas que ya trabajan con tecnología Microsoft, por lo bien que se integra con .NET, Excel, Power BI y Azure.

Consola: sqlcmd · Interfaz: SSMS, Azure Data Studio · Puerto 1433

Ventajas y desventajas

CostoGratis, sin límitesLicencia paga; Express gratis hasta 10 GB
A favorEstándar, extensible, excelente con JSON y datos geográficosHerramientas muy pulidas, integración con el stack Microsoft

Se usa enStartups, ciencia de datos, aplicaciones webEmpresas grandes, sistemas de gestión, reportería corporativa
Cuál elegir. Si arrancás de cero y podés elegir, PostgreSQL: es gratis, es estándar y lo que aprendas se traslada mejor a cualquier otro motor. Si trabajás en una empresa que ya corre SQL Server, la decisión está tomada y no es mala: la herramienta es sólida.

Lo que es igual en los dos

La estructura de una consulta y casi todos los operadores. Esto corre idéntico:

SELECT c.nombre, COUNT(*) AS compras, SUM(v.monto) AS total
FROM ventas v
INNER JOIN clientes c ON v.id_cliente = c.id
WHERE v.fecha >= '2026-01-01'
  AND v.monto IS NOT NULL
GROUP BY c.nombre
HAVING SUM(v.monto) > 1000
ORDER BY total DESC;

La misma consulta en los dos dialectos

PostgreSQL

SELECT nombre || ' ' || apellido AS completo,
       COALESCE(saldo, 0) AS saldo
FROM clientes
WHERE nombre ILIKE 'ana%'
ORDER BY alta DESC
LIMIT 10;

SQL Server

SELECT TOP 10
       nombre + ' ' + apellido AS completo,
       ISNULL(saldo, 0) AS saldo
FROM clientes
WHERE nombre LIKE 'ana%'
ORDER BY alta DESC;
La diferencia que más sorprende.

En PostgreSQL, comparar texto distingue mayúsculas: WHERE ciudad = 'cordoba' no encuentra 'Córdoba' ni 'CORDOBA'.

En SQL Server, con la configuración habitual, no distingue: esas tres formas se consideran iguales. Una consulta que anda en un motor puede devolver cero filas en el otro sin dar ningún error.

Cómo leer esta guía. Cuando veas un solo bloque de código, corre igual en los dos motores — que es la mayoría de los casos. Cuando veas dos columnas, ahí hay una diferencia real de dialecto y conviene prestarle atención.
Clave. Aprendé el SQL estándar y tratá las diferencias como lo que son: detalles de traducción. Si sabés consultar en uno, en el otro te faltan diez palabras, no un idioma nuevo.

Sección 02

Estructura de una consulta

Toda consulta se arma con las mismas cláusulas, siempre en el mismo orden de escritura. Pero el motor no las ejecuta en ese orden, y entender eso resuelve la mitad de los errores.

Cómo se escribe

SELECT   columnas
FROM     tabla
JOIN     otra ON condición
WHERE    filtro de filas
GROUP BY columnas de agrupación
HAVING   filtro de grupos
ORDER BY columnas de orden;

Cómo se ejecuta

Por eso esto falla. 
SELECT precio * cantidad AS total
FROM ventas
WHERE total > 1000;   -- ✗ column "total" does not exist
Cuando corre el WHERE, el alias total todavía no fue creado. Hay que repetir la expresión: WHERE precio * cantidad > 1000. En el ORDER BY, en cambio, el alias sí funciona, porque va después del SELECT.

Convenciones de escritura

PrácticaPor qué
Palabras clave en MAYÚSCULASepara de un vistazo la sintaxis de tus tablas y columnas
Una cláusula por líneaHace legible una consulta larga y facilita comentar partes
Alias cortos de tablaventas v evita repetir y previene ambigüedades
Evitar SELECT *Trae columnas que no usás y se rompe si cambia la tabla
Terminar con ;Obligatorio si mandás varias sentencias juntas
Clave. Cuando una consulta no anda, leela en orden de ejecución, no de escritura: qué tablas hay, qué filas sobreviven al filtro, cómo se agrupan y recién ahí qué se muestra.

Sección 03

Filtrar con WHERE

Quedarse con las filas que cumplen una condición. Es la cláusula que más impacta en el rendimiento y en que el resultado sea el correcto.

Recetario

-- Comparación
WHERE monto > 1000
WHERE estado = 'activo'
WHERE monto <> 0              -- distinto (también vale !=)

-- Combinar condiciones
WHERE monto > 1000 AND estado = 'activo'
WHERE (ciudad = 'CABA' OR ciudad = 'Rosario') AND activo

-- Pertenencia y rangos
WHERE ciudad IN ('CABA', 'Rosario', 'Córdoba')
WHERE monto BETWEEN 100 AND 500        -- incluye los dos extremos
WHERE fecha >= '2026-01-01' AND fecha < '2026-02-01'

-- Texto
WHERE nombre LIKE 'Ana%'            -- empieza con Ana
WHERE mail LIKE '%@gmail.com'       -- termina con
WHERE cod LIKE 'A_2'                -- _ es exactamente un carácter

-- Nulos
WHERE telefono IS NULL
WHERE telefono IS NOT NULL

-- Negar
WHERE NOT estado = 'baja'
WHERE ciudad NOT IN ('CABA', 'Rosario')

Diferencias entre motores

PostgreSQL

-- Distingue mayúsculas
WHERE ciudad = 'CABA'

-- Para ignorarlas: ILIKE
WHERE ciudad ILIKE 'caba'
WHERE LOWER(ciudad) = 'caba'

SQL Server

-- No distingue (config. habitual)
WHERE ciudad = 'caba'
-- encuentra 'CABA' igual

-- No existe ILIKE
WHERE LOWER(ciudad) = 'caba'
Los tres errores clásicos.

1. Comparar contra NULL con =. WHERE telefono = NULL no devuelve nada nunca, ni siquiera error. NULL significa "desconocido" y no es igual a nada. Va IS NULL.

2. Olvidar los paréntesis al mezclar AND y OR. AND se evalúa primero, así que a = 1 OR b = 2 AND c = 3 significa a = 1 OR (b = 2 AND c = 3), que rara vez es lo que querías.

3. NOT IN con una lista que contiene NULL. Devuelve cero filas siempre. Si la lista viene de una subconsulta, filtrá los nulos ahí o usá NOT EXISTS.

Tip — rangos de fechas. Preferí fecha >= '2026-01-01' AND fecha < '2026-02-01' antes que BETWEEN '2026-01-01' AND '2026-01-31'. Si la columna guarda hora además de fecha, el BETWEEN deja afuera todo lo que pasó el 31 después de medianoche.
Clave. Evitá envolver la columna en una función dentro del WHERE: WHERE YEAR(fecha) = 2026 obliga al motor a recorrer toda la tabla. WHERE fecha >= '2026-01-01' AND fecha < '2027-01-01' devuelve lo mismo y puede usar el índice.

Sección 04

Ordenar y limitar

Presentar el resultado en un orden determinado y quedarse con las primeras filas. Acá está la diferencia de sintaxis más visible entre los dos motores.

Ordenar — igual en los dos

ORDER BY monto DESC
ORDER BY ciudad ASC, monto DESC     -- varias claves
ORDER BY total DESC                  -- el alias del SELECT acá sí vale
ORDER BY 2 DESC                      -- por posición: evitalo, es frágil

Limitar — acá cambia

PostgreSQL

SELECT * FROM ventas
ORDER BY monto DESC
LIMIT 10;

-- Paginar: saltear 20
SELECT * FROM ventas
ORDER BY monto DESC
LIMIT 10 OFFSET 20;

SQL Server

SELECT TOP 10 * FROM ventas
ORDER BY monto DESC;

-- Paginar: saltear 20
SELECT * FROM ventas
ORDER BY monto DESC
OFFSET 20 ROWS
FETCH NEXT 10 ROWS ONLY;

Dónde van los nulos

MotorPor defectoPara cambiarlo
PostgreSQLLos NULL van al final en ASCNULLS FIRST / NULLS LAST
SQL ServerLos NULL van al principio en ASCUn CASE auxiliar en el ORDER BY
Limitar sin ordenar no tiene sentido. Sin ORDER BY, "las primeras 10 filas" son las que el motor devuelva primero, y eso puede cambiar entre ejecuciones. Si querés las 10 más grandes, ordená. En SQL Server el OFFSET … FETCH directamente exige ORDER BY.
Clave. Para paginar de forma consistente, ordená por algo único. Si hay empates en la columna de orden, las filas repetidas pueden aparecer en dos páginas o en ninguna: agregá el id como segundo criterio.

Sección 05

Funciones y NULL

Transformar valores dentro de la consulta. Es donde más se separan los dialectos, así que conviene tener la tabla de equivalencias a mano.

Texto

PostgreSQL

LENGTH(nombre)
UPPER(nombre) / LOWER(nombre)
SUBSTRING(nombre, 1, 3)
TRIM(nombre)
nombre || ' ' || apellido
POSITION('@' IN mail)

SQL Server

LEN(nombre)
UPPER(nombre) / LOWER(nombre)
SUBSTRING(nombre, 1, 3)
TRIM(nombre)

CHARINDEX('@', mail)
Tip — CONCAT funciona en los dos. CONCAT(nombre, ' ', apellido) evita elegir entre || y +, y además ignora los NULL en vez de convertir todo el resultado en NULL. Si querés código portable entre motores, usalo.

Fechas

Nulos y condicionales

-- COALESCE y NULLIF funcionan en los dos motores
COALESCE(telefono, 'sin dato')      -- el primer valor no nulo
COALESCE(movil, fijo, 'sin dato')    -- admite varios
NULLIF(divisor, 0)                  -- evita dividir por cero

-- CASE: el if/else de SQL, idéntico en ambos

FROM ventas;

El NULL contagia. Cualquier operación con NULL da NULL: 100 + NULL es NULL, y 'Ana' || NULL también. Si una columna calculada te da vacía sin motivo, buscá el nulo escondido y envolvelo en COALESCE.
Clave. COALESCE y CASE son estándar y andan en los dos motores. Si escribís pensando en ellos en vez de en ISNULL o IIF, tus consultas se mudan de motor sin tocar nada.

Sección 06

Combinar tablas con JOIN

En una base relacional los datos están repartidos en varias tablas a propósito. El JOIN los vuelve a juntar en el momento de consultarlos, cruzando por una columna en común.

La forma base

SELECT v.id, c.nombre, v.monto
FROM ventas v
LEFT JOIN clientes c ON v.id_cliente = c.id;

Se lee: partí de ventas, traé clientes, y emparejá las filas donde id_cliente coincida con id. La tabla del FROM es la izquierda; la del JOIN, la derecha.

Qué pasa fila por fila

Los cuatro tipos

TipoDevuelveUsalo para
INNER JOINSolo las filas que coinciden en ambasCuando la pareja es obligatoria
LEFT JOINTodas las de la izquierda, coincidan o noAgregar datos sin perder filas
RIGHT JOINIgual, pero al revésPoco usado: se da vuelta el LEFT
FULL JOINTodo, de las dosComparar dos fuentes

Recetario

-- Cruce simple
SELECT v.*, c.nombre
FROM ventas v
INNER JOIN clientes c ON v.id_cliente = c.id;

-- Varias tablas encadenadas
SELECT v.id, c.nombre, p.descripcion
FROM ventas v
LEFT JOIN clientes  c ON v.id_cliente  = c.id
LEFT JOIN productos p ON v.id_producto = p.id;

-- Buscar huérfanos: ventas sin cliente cargado
SELECT v.*
FROM ventas v
LEFT JOIN clientes c ON v.id_cliente = c.id
WHERE c.id IS NULL;

-- JOIN con condición extra
SELECT v.id, c.nombre
FROM ventas v
LEFT JOIN clientes c
       ON v.id_cliente = c.id
      AND c.activo = TRUE;

-- La tabla consigo misma (jerarquías)
SELECT e.nombre AS empleado, j.nombre AS jefe
FROM empleados e
LEFT JOIN empleados j ON e.id_jefe = j.id;
Los tres errores clásicos.

1. Filtrar la tabla derecha en el WHERE. Poner WHERE c.activo = TRUE convierte tu LEFT JOIN en un INNER JOIN sin que te des cuenta: las filas sin pareja tienen NULL ahí y el filtro las descarta. Si la condición es parte del cruce, va en el ON.

2. Olvidar el ON. Sin condición de cruce se combina cada fila con todas las de la otra tabla. Con 1.000 y 1.000 filas te da un millón de resultados.

3. Que se multipliquen las filas. Si la clave está repetida en la tabla derecha, cada coincidencia genera una fila. Contá antes: SELECT id, COUNT(*) FROM clientes GROUP BY id HAVING COUNT(*) > 1;

Diferencias entre motores

En el JOIN en sí no hay ninguna: la sintaxis es idéntica en PostgreSQL y en SQL Server, incluido FULL OUTER JOIN. Lo que cambia es lo que suele acompañarlo, cuando querés quedarte con las primeras filas del cruce:

PostgreSQL

SELECT c.nombre, SUM(v.monto) AS total
FROM ventas v
JOIN clientes c ON v.id_cliente = c.id
GROUP BY c.nombre
ORDER BY total DESC
LIMIT 5;

SQL Server

SELECT TOP 5
       c.nombre, SUM(v.monto) AS total
FROM ventas v
JOIN clientes c ON v.id_cliente = c.id
GROUP BY c.nombre
ORDER BY total DESC;
Nota. INNER JOIN y JOIN a secas son lo mismo en los dos motores, igual que LEFT JOIN y LEFT OUTER JOIN. Escribir la palabra completa es más claro para quien lea la consulta después.

Alternativas

En vez de JOINCuándo conviene
EXISTSSolo querés saber si hay coincidencia, sin traer columnas
IN (subconsulta)Filtrar por una lista corta de valores
UNION ALLApilar filas de dos tablas, no cruzarlas
WITH … ASLa consulta creció: partirla en pasos con nombre
Tip — usá alias siempre. ventas v y clientes c te ahorran escribir y, sobre todo, evitan el error column reference "id" is ambiguous cuando las dos tablas tienen una columna con el mismo nombre. Con alias siempre queda claro de cuál hablás.
Clave. Ante la duda, LEFT JOIN. Conserva todas las filas de tu tabla principal y los NULL que aparecen te muestran dónde faltan datos. El INNER JOIN borra esas filas en silencio, y ese silencio es el que te hace perder registros sin notarlo.

Sección 07

Agrupar con GROUP BY

Colapsar muchas filas en una por categoría, calculando un total, un promedio o un conteo. Es la base de cualquier reporte.

Dónde filtra cada cláusula

Recetario

-- Las cinco funciones de agregación
SELECT COUNT(*)      AS filas,
       COUNT(mail)   AS con_mail,   -- COUNT de columna ignora NULL
       SUM(monto)     AS total,
       AVG(monto)     AS promedio,
       MIN(monto)     AS minimo,
       MAX(monto)     AS maximo
FROM ventas;

-- Por categoría
SELECT ciudad, COUNT(*) AS ventas, SUM(monto) AS total
FROM ventas
GROUP BY ciudad
ORDER BY total DESC;

-- Filtrar antes y después de agrupar
SELECT ciudad, SUM(monto) AS total
FROM ventas
WHERE fecha >= '2026-01-01'      -- filas: antes de agrupar
GROUP BY ciudad
HAVING SUM(monto) > 10000       -- grupos: después
ORDER BY total DESC;

-- Agrupar por varias columnas
SELECT ciudad, vendedor, SUM(monto) AS total
FROM ventas
GROUP BY ciudad, vendedor;

-- Contar valores distintos
SELECT COUNT(DISTINCT id_cliente) AS clientes FROM ventas;
Todo lo del SELECT va en el GROUP BY.

Si seleccionás una columna que no está agregada, tiene que estar en el GROUP BY. Los dos motores fallan con column "x" must appear in the GROUP BY clause o su equivalente.

Y ojo con COUNT(*) contra COUNT(columna): el primero cuenta filas, el segundo cuenta valores no nulos. En una columna con nulos dan distinto.

WHERE o HAVING

CláusulaFiltraPuede usar
WHEREFilas, antes de agruparColumnas comunes
HAVINGGrupos, después de agruparFunciones de agregación
Clave. Si la condición se puede escribir en el WHERE, escribila ahí: filtrar antes de agrupar significa agrupar menos filas, y eso es más rápido. Dejá el HAVING solo para lo que depende del resultado agregado.

Sección 08

Subconsultas y CTE

Usar el resultado de una consulta dentro de otra. Sirve para resolver en pasos lo que no entra en una sola sentencia.

Las tres formas

-- 1. Subconsulta que devuelve UN valor
SELECT nombre, monto
FROM ventas
WHERE monto > (SELECT AVG(monto) FROM ventas);

-- 2. Subconsulta que devuelve UNA LISTA
SELECT *
FROM clientes
WHERE id IN (SELECT id_cliente FROM ventas WHERE monto > 5000);

-- 3. Subconsulta como tabla (hay que ponerle alias)
SELECT ciudad, total
FROM (SELECT ciudad, SUM(monto) AS total
      FROM ventas GROUP BY ciudad) t
WHERE total > 10000;

CTE: lo mismo, pero legible

Un WITH le pone nombre a cada paso y se lee de arriba hacia abajo. Funciona igual en los dos motores y es la forma recomendada cuando la consulta crece:

WITH ventas_2026 AS (
    SELECT * FROM ventas WHERE fecha >= '2026-01-01'
),
totales AS (
    SELECT ciudad, SUM(monto) AS total
    FROM ventas_2026
    GROUP BY ciudad
)
SELECT ciudad, total
FROM totales
WHERE total > 10000
ORDER BY total DESC;

EXISTS, la más eficiente para "¿hay alguno?"

-- Clientes que compraron alguna vez
SELECT c.*
FROM clientes c
WHERE EXISTS (SELECT 1 FROM ventas v WHERE v.id_cliente = c.id);

-- Clientes que nunca compraron
SELECT c.*
FROM clientes c
WHERE NOT EXISTS (SELECT 1 FROM ventas v WHERE v.id_cliente = c.id);

Cuál usar

FormaCuándo
WITH … ASPor defecto: la consulta tiene más de un paso
EXISTSSolo importa si hay coincidencia, no los datos
IN (subconsulta)Lista corta y sin nulos
JOINNecesitás columnas de la otra tabla
NOT IN y los nulos. Si la subconsulta de un NOT IN devuelve aunque sea un NULL, el resultado es cero filas. Siempre. Usá NOT EXISTS, que no tiene ese problema.
Clave. Ante una consulta que no te sale, partila en CTE. Cada WITH lo podés probar por separado hasta que devuelva lo que esperás, y después encadenarlos.

Sección 09

Funciones de ventana

Calcular un valor agregado sin perder el detalle de cada fila. Es lo que permite responder "cuánto representa esta venta sobre el total de su ciudad" en una sola consulta.

La diferencia con GROUP BY

Recetario — igual en los dos motores

-- Total de la ciudad al lado de cada venta
SELECT id, ciudad, monto,
       SUM(monto) OVER (PARTITION BY ciudad) AS total_ciudad
FROM ventas;

-- Numerar y rankear
SELECT nombre, monto,
       ROW_NUMBER() OVER (ORDER BY monto DESC) AS puesto,
       RANK()       OVER (ORDER BY monto DESC) AS rank_con_empates
FROM ventas;

-- El top 3 de cada ciudad
WITH ranking AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY ciudad
                                ORDER BY monto DESC) AS pos
    FROM ventas
)
SELECT * FROM ranking WHERE pos <= 3;

-- Comparar con la fila anterior
SELECT mes, total,
       LAG(total) OVER (ORDER BY mes) AS mes_anterior,
       total - LAG(total) OVER (ORDER BY mes) AS variacion
FROM resumen_mensual;

-- Acumulado
SELECT fecha, monto,
       SUM(monto) OVER (ORDER BY fecha) AS acumulado
FROM ventas;

Las que más se usan

FunciónDevuelve
ROW_NUMBER()1, 2, 3… sin empates
RANK()Empata y saltea: 1, 1, 3
DENSE_RANK()Empata sin saltear: 1, 1, 2
LAG() / LEAD()El valor de la fila anterior o siguiente
SUM() OVERTotal del grupo, o acumulado si hay ORDER BY
No se pueden usar en el WHERE. Las funciones de ventana se calculan después del WHERE y del GROUP BY. Para filtrar por un ROW_NUMBER() hay que calcularlo en un CTE y filtrar afuera, como en el ejemplo del top 3.
Clave. Leé OVER (PARTITION BY x ORDER BY y) como "para cada x, ordenando por y". PARTITION BY es el GROUP BY de la ventana, y ORDER BY define si el cálculo es del grupo entero o acumulado hasta esa fila.

Sección 10

Insertar, actualizar y borrar

Las tres sentencias que modifican datos. A diferencia de un SELECT, acá un error deja consecuencias.

Recetario — igual en los dos motores

-- Insertar
INSERT INTO clientes (nombre, ciudad, alta)
VALUES ('Ana', 'CABA', '2026-03-01');

-- Varias filas de una vez
INSERT INTO clientes (nombre, ciudad)
VALUES ('Ana', 'CABA'),
       ('Beto', 'Rosario');

-- Insertar el resultado de una consulta
INSERT INTO resumen (ciudad, total)
SELECT ciudad, SUM(monto) FROM ventas GROUP BY ciudad;

-- Actualizar
UPDATE clientes
SET ciudad = 'CABA', activo = TRUE
WHERE id = 42;

-- Borrar
DELETE FROM clientes WHERE id = 42;
Sin WHERE, afecta todo.

UPDATE clientes SET activo = FALSE; da de baja a todos. DELETE FROM clientes; vacía la tabla. Ninguna de las dos pide confirmación.

Costumbre que salva: escribí primero el SELECT con ese mismo WHERE. Si devuelve las filas que esperabas, recién ahí cambiás SELECT * por UPDATE o DELETE.

Diferencias entre motores

PostgreSQL

-- Ver lo que se insertó
INSERT INTO clientes (nombre)
VALUES ('Ana')
RETURNING id;

-- UPDATE con otra tabla
UPDATE ventas v
SET zona = c.zona
FROM clientes c
WHERE v.id_cliente = c.id;

-- Transacción
BEGIN;
  UPDATE …;
COMMIT;   -- o ROLLBACK;

SQL Server

-- Ver lo que se insertó
INSERT INTO clientes (nombre)
OUTPUT INSERTED.id
VALUES ('Ana');

-- UPDATE con otra tabla
UPDATE v
SET v.zona = c.zona
FROM ventas v
JOIN clientes c ON v.id_cliente = c.id;

-- Transacción
BEGIN TRANSACTION;
  UPDATE …;
COMMIT;   -- o ROLLBACK;
Tip — probá dentro de una transacción. Abrí la transacción, corré el UPDATE, verificá con un SELECT que quedó como querías, y recién ahí COMMIT. Si algo salió mal, ROLLBACK deja todo como estaba.
Clave. DELETE borra filas y se puede filtrar; TRUNCATE vacía la tabla entera de un saque y es mucho más rápido, pero no admite WHERE ni se deshace con la misma facilidad. Para limpiar una tabla de trabajo, TRUNCATE; para todo lo demás, DELETE con WHERE.

Sección 11

Crear tablas

Definir la estructura: qué columnas hay, de qué tipo, y qué reglas garantizan que los datos tengan sentido.

Una tabla con sus restricciones

PostgreSQL

CREATE TABLE clientes (
  id      INT GENERATED ALWAYS AS IDENTITY
          PRIMARY KEY,
  nombre  VARCHAR(100) NOT NULL,
  mail    VARCHAR(150) UNIQUE,
  saldo   NUMERIC(12,2) DEFAULT 0,
  activo  BOOLEAN DEFAULT TRUE,
  alta    DATE DEFAULT CURRENT_DATE
);

SQL Server

CREATE TABLE clientes (
  id      INT IDENTITY(1,1)
          PRIMARY KEY,
  nombre  VARCHAR(100) NOT NULL,
  mail    VARCHAR(150) UNIQUE,
  saldo   DECIMAL(12,2) DEFAULT 0,
  activo  BIT DEFAULT 1,
  alta    DATE DEFAULT GETDATE()
);

Claves y relaciones

-- Clave foránea: garantiza que el cliente exista
CREATE TABLE ventas (
  id          INT PRIMARY KEY,
  id_cliente  INT NOT NULL REFERENCES clientes(id),
  monto       NUMERIC(12,2) CHECK (monto >= 0),
  fecha       DATE NOT NULL
);

-- Modificar una tabla existente
ALTER TABLE clientes ADD telefono VARCHAR(30);

Sección 12

Índices y rendimiento

Cuando una consulta tarda, casi siempre es porque el motor está leyendo la tabla entera. Un índice es un atajo para encontrar filas sin recorrer todo.

Crear un índice — igual en los dos

CREATE INDEX idx_ventas_fecha ON ventas(fecha);
CREATE INDEX idx_ventas_cli ON ventas(id_cliente);
CREATE INDEX idx_compuesto ON ventas(ciudad, fecha);   -- el orden importa
DROP INDEX idx_ventas_fecha;

Qué conviene indexar

IndexarNo indexar
Columnas del WHERE frecuenteTablas chicas: leerlas entera es más rápido
Claves foráneas usadas en JOINColumnas con pocos valores distintos
Columnas del ORDER BY habitualTablas con muchísima escritura

Ver qué está haciendo el motor

PostgreSQL

EXPLAIN ANALYZE
SELECT * FROM ventas
WHERE fecha >= '2026-01-01';

-- Buscá en la salida:
--   Seq Scan  → lee todo (mal)
--   Index Scan → usa el índice

SQL Server

SET STATISTICS IO ON;
SELECT * FROM ventas
WHERE fecha >= '2026-01-01';

-- O el plan gráfico en SSMS:
--   Table Scan → lee todo (mal)
--   Index Seek → usa el índice
El índice se anula si envolvés la columna. WHERE YEAR(fecha) = 2026 obliga a calcular la función en cada fila, así que el índice sobre fecha queda inservible. Reescribilo como un rango: WHERE fecha >= '2026-01-01' AND fecha < '2027-01-01'. Lo mismo con LIKE '%texto%': el comodín al principio impide usar el índice.
Clave. Los índices aceleran la lectura y frenan la escritura, porque hay que mantenerlos en cada INSERT y UPDATE. No indexes por las dudas: medí primero cuál consulta es lenta, y creá el índice que esa consulta necesita.

Consultas que siempre se repiten

-- Cuántas filas hay y cuántos duplicados
SELECT COUNT(*) FROM tabla;
SELECT id, COUNT(*) FROM tabla GROUP BY id HAVING COUNT(*) > 1;

-- Cuántos nulos tiene una columna
SELECT COUNT(*) FROM tabla WHERE col IS NULL;

-- Qué valores distintos hay y con qué frecuencia
SELECT col, COUNT(*) AS veces
FROM tabla GROUP BY col ORDER BY veces DESC;

-- Filas de una tabla que no tienen pareja en la otra
SELECT a.* FROM a
LEFT JOIN b ON a.id = b.id_a
WHERE b.id_a IS NULL;

-- El registro más reciente de cada grupo
WITH r AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY id_cliente
                              ORDER BY fecha DESC) AS n
  FROM ventas
)
SELECT * FROM r WHERE n = 1;
